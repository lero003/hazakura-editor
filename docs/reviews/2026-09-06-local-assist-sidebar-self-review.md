## 判断

ユーザーの「ページ選択＋行選択＋会話、その案を差分確認」という方向を採用する。
NotionのAI能力との同等性ではなく、編集対象と依頼を同じ場所で扱う配置の参考とする。
このブランチではメインウィンドウ内の任意サイドパネルを標準の入口にする。
従来の分離ウィンドウのネイティブ経路は互換性のため残す。
公開済み2.6.2の変更・マージ・配布を意味しない。

## 自己レビューで修正した点

### 生成無効化とネイティブ処理の寿命が一致していなかった

旧hookは文書切替・本文変更で提案と生成ロックを解除しても、実際のhelperを停止しなかった。
また、単一helperに複数の未完了リクエストを渡せる状態だった。
変更後は無効化時に結果の所有権を先に失効させ、開始済みのhelperへ停止を要求する。
生成Promiseが終了するまでbusyとロックを維持し、次の生成を受け付けない。
同じrequestIdの重複配信は無視する。ストア通知からの同期的な再入にも予約で対処する。
停止要求自体に失敗した場合も、遅い結果は反映せず、終了まで新規生成を抑止する。

### 別対象・別会話の案が失敗後に復元され得た

従来のprevious proposal保持は文書セッションだけで区別していた。
このため新しい対象や会話の生成に失敗すると、それ以前の無関係な案が再表示され得た。
実際のストアを使う限定チェックで変更前の失敗を再現し、修正後の成功を確認した。
復元可能な案をconversationId / path / session / range / target text / original textが一致するものに限定した。

### 追加画面と既存の反映処理を分岐させない

サイドパネルから、分離窓専用の `request_apple_assist_proposal` コマンドは呼ばない。
同一WebView内のbridgeで既存のメインhookへ依頼し、同じproposal storeとApply callbackを利用する。
Rustのwindow label / distribution gateを緩めず、新たな本文setterや生成の別実装も追加しない。
既存レビューはパネル内か従来位置の片方だけに表示する。
取消後のhelper終了待ちでは、パネル内のApply/Discardも無効にする。

## 新しい体験

1. ページは開いているテキスト文書から選ぶ。「別の文書を開く…」は既存のファイル選択操作を使う。
2. 編集対象を「本文の選択」「元の文章の行番号」「文書全体」から明示的に選ぶ。
3. 最初の依頼、または「対象を確認して固定」で元文章を固定する。カーソル移動では追従しない。
4. 依頼と短い生成状態を会話欄で確認し、完成した案に追加依頼する。
5. 共通レビューの「差分／変更後／元の文章」で確認し、「文書へ反映」で一度だけ反映する。
6. 対象を選び直すときは会話と未反映案の破棄を明示確認する。反映・破棄後の会話は次の対象に引き継がない。

開いている文書セッションごとに入力中の依頼と会話をメモリ保持し、パネルを閉じても維持する。
タブを閉じると該当会話を取り除き、同じパスを開き直した別セッションには移さない。
会話表示は直近20件、モデルへの依頼履歴は既存の直近4件・各500文字の上限を保つ。
失敗・取消した依頼は成功履歴へ入れず、次の入力がなければcomposerへ戻す。
生成中に次の依頼を書き置いても、それを生成完了通知で消さない。

行指定は表示上の折り返しではなくsourceの行番号を使う。
最終行の区切り改行は置換範囲に含めず、部分行編集が隣の行と結合しないようにする。
4,000文字は既存backendと同じUnicode code point単位で判定し、超過時に黙って短縮しない。
通常幅は横配置、狭幅は上下配置。L Modeの固定action railにheaderが重ならない余白を持たせる。
Enterは改行、⌘Enter/Ctrl+Enterは送信、IME変換確定中は送信しない。
Escape/閉じる操作はパネルのみを閉じ、生成中の停止は専用ボタンで行う。
