### 実機第4弾・第10報（お遊びテーマの演出復活）

オーナーの指摘: 「CRT / 江戸彼岸は全くリッチ要素が無い。オープニングは動くが、それ以上の
演出が無い。深海はワークスペースだけ動く。お遊びテーマなので“遊び”を明確に。全部戻す必要は
ないが演出はする（負荷は多少かけて良い）」。

**原因**: 演出（WebGL）は不透明な紙の**後ろ**（`z-index: var(--z-base)`）に居たため、
ペインが覆う範囲では見えず、背景の隙間（ワークスペース）だけ動いていた。

方針（オーナー選択）: **面を透かして背景の動きを見せる＋前景の演出を一段戻す。
タブ・ツールバー・ステータスは静かなまま**（読みやすさは守る）。負荷は見た目優先。

| 変更 | 内容 |
|---|---|
| 紙を透かす | crt/shinkai `--surface-paper: rgba(..., 0.9)`、edohigan `rgba(..., 0.93)`（`--cm-bg` も追随） |
| 江戸彼岸の花びら | `z-base` → `calc(var(--z-dropdown) - 10)`（面の上・モーダルより下）、opacity 0.25→0.18、multiply 維持 |
| 江戸彼岸の淡い光 | 同上の層へ、`normal` → `soft-light` |
| フレーム上限 | normal 30fps → **60fps**、subtle 24 → 30fps（DPR 2 は維持） |

**契約の置き換え**: `themeContrast.test.ts` の「**不透明な紙**」を「**透かしても読める**」へ。
半透明の紙を地色と合成し、本文・補助文字が AA（4.5:1）以上であること＋ alpha ≥ 0.88 を検査
（`resolvedPaper` / `blendOver` / `hexToChannels` を追加）。

実描画（fixture・実DOM実測）:
- crt: paper `rgba(13, 26, 17, 0.9)` / canvas z=1（背後＝透けて見える）/ overlay z=1200 multiply（前景スキャン）
- shinkai: paper `rgba(20, 56, 74, 0.9)` / canvas z=1 / overlay z=1200 screen
- edohigan: paper `rgba(255, 252, 248, 0.93)` / canvas z=90 opacity 0.18 multiply / overlay z=90 soft-light

画像: `theme-play-crt.png` / `theme-play-edohigan.png`。WebGL の中身はヘッドレスで
キャプチャが不安定なため、層と透け具合は computed style で確認している（映像の最終確認は実機）。

### 実機第4弾・第12報（江戸彼岸のシェーダーを書き直す）

オーナーの指摘: 「江戸彼岸は特別にしようとしてイマイチ。演出を気にせずシェーダーを
書き直して。一番リッチでもいいが、**ハザクラエディタらしさ**を演出したい」。

**設計**: 「葉桜の余白に、光が差す」。深海（水）の骨格は借りない。
- 主役は **木漏れ日**（domain warp した fbm のまだら）。光と翳りは**同じ場**から作り、
  影を引かなかった場所＝紙がそのまま見える場所が「光」として読める。
- 舞うのは花びらではなく **葉の影**（SDF の葉＋主脈。ゆっくり落ち、風＝速度場で流れる）。
  花びらは 2 枚だけ（葉桜＝終わりかけの花）。埃、紙の質感、光の向き、端の翳り。
- 「余白」＝画面の大半は動かない。周期は 60〜90s。

**この過程で見つけた実バグ 2 件（どちらも江戸彼岸だけ取り残された旧仕様）**:
1. `preview.css` の `.preview-pane-preview .markdown-preview` に、紙の上 30% を
   `#3a2838`（暗い茶紫）から紙へ抜けるグラデーションが残っていた。明るい紙のテーマなのに
   **プレビュー上部に暗い帯**が出ていた（crt/shinkai は `var(--preview-reading-surface)` に
   統一済みで、江戸彼岸だけ旧仕様）。同じ扱いに修正。
2. `workspace.css` の `.preview-pane-card` に edohigan/shinkai/yakou 用の**暗いカード
   グラデーション**が残っていた。読み面の正本は `--preview-reading-surface`
   （= `--surface-paper`）で、themeContrast の契約もそれを前提にしている。撤去。

**合成の学び（実測）**: `soft-light` は #fffcf8 のような**ほぼ白い紙では実効 1%**
（`sqrt(base) - base → 0`）。影で見せるなら `multiply`。合成後の画素実測で
「まだら」の差が **10% 前後**（245 → 218）になるまで振幅を上げた。
シェーダ単体の画素（canvas を 2D に写して計測）でも 142〜255 の分布を確認。

**現状**: 効果は出ており、文字は全く読める。ただし判定（外部の目）のスコアは
4/10 → 2/10 と安定せず、**葉の形が「葉」として読めるか**が最後の課題。
次の一手は「葉をもう一段大きく・濃く・尖らせ、枚数をさらに絞る」。
最終判断は実機のオーナーの目で。

### 実機第4弾・第13報（江戸彼岸を弱める／曙光・夜行の演出を見せる）

オーナーの指摘: 「江戸彼岸は葉っぱが大きすぎ、背景のコントラストが強すぎて文字が読みづらい
（雲っぽさはある）。曙光／夜行は何もアニメーションが見えない」。

**江戸彼岸**
- まだらのセルを約半分に（`p * 4.6` → `p * 8.0`）。大きすぎて「巨大な葉」に見えていた
  （実機の見え方で 180〜220px → 葉は 23〜37px 相当へ）。
- 影の濃さを戻す: まだら 0.36 → 0.205、葉 0.40-0.58 → 0.22-0.34、clamp 0.70 → 0.46、
  紙への適用 opacity 0.5 → 0.38。紙のまだら差は実測 **20/255（約8%）**。

**曙光／夜行（原因と対策）**
- 演出（`bgDrift`）は `.app-shell` の**下地**にあり、不透明なペインの後ろで
  隙間からしか見えていなかった（＝「何も見えない」）。
- 同じグラデーションを**トークンに集約**（`--ambient-aurora` / `--ambient-dawn`）し、
  下地と**面の上に薄く重ねる層**（`.ambient-yakou::before` / `.ambient-shokou::before`、
  z は `calc(var(--z-dropdown) - 10)` = モーダルより下）で共有。
- 重ねる層は色を**不透明**で持ち、`opacity` で薄くする（背景用の rgba 色は重ねると消える：
  実測で差 0 だった）。夜行は `screen`（暗い地に色を灯す）、曙光は `color`
  （**明度を動かさず色相だけ移す**ので文字の読みやすさに影響しない）。
- 実測（面の上の画素の ON/OFF 差）: 夜行 **[+10, +8, +19]** / 曙光 **[+8, -9, -21]**。

契約テスト `editorCss.test.ts` を新構造（トークン＋重ねる層）に追随。

### 実機第4弾・第14報（江戸彼岸に「動き」／曙光を淡く）

オーナー判断:「曙光は優しい黄と青で綺麗で曙光っぽいが、エディタとしては悩ましい
（まあいいか）。江戸彼岸はまだまだやれる」。→ 江戸彼岸=**動きの演出**、曙光=**少し淡く**。

**江戸彼岸の動き（突風）**
- 位置を直接動かすと葉が飛ぶので、**時間そのものを前後に揺らす**方式にした
  （`gustWave(t) = pow(0.5 + 0.5*sin(t*0.085 + 1.7*sin(t*0.019)), 9)`）。
  速度だけが変わるので不自然な跳びがなく、「ふっと流れて、また静かに戻る」になる。
- 揺らした時間 `wt` を **葉・埃・光**の3つに配る（まとめて風に流れる＝世界が1つに見える）。
  光は `t + 2.5*gust` で少しだけ速く動く（枝が揺れる気配）。
- 実測: 波形は 30〜70 秒おきに立ち上がり、間は 0.00（平均 0.25 → 指数を 5→9 にして
  さらに短く鋭く）。GLSL はコンパイル成功、葉が `wt` を使っていることも確認。

**曙光**
- 重ねる層の opacity 0.42 → **0.25**（色は残し、紙面の主張を弱める）。
  `color` 合成なので明度は動かず、読みやすさは元から影響しない。

備考: fixture での「動き」の画素読み出しは当てにならない（WebGL の readback が
不安定＋大きい base64 でブラウザが落ちる）。u_time は performance.now() で進む実装で、
他テーマの演出が実機で動いていることが動作の証拠。最終確認は実機。

## 決定（2026-09-11・オーナー）

## 追記 — 「起動直後と操作後で信号機が動いて見える」（2026-09-11 第2報）

実機で「ボタンの位置が相対的に動いていく」「起動時とそれ以外で別の指定がありそう」との指摘。

**調べたこと**

1. **ネイティブ側は一度きり**。`src-tauri/src/lib.rs` の `on_window_event` は
   Apple Assist ウィンドウの閉じ処理だけで、**実行時に信号機を動かすコードは無い**
   （`set_traffic_light_position` の類も無し）。`trafficLightPosition` はウィンドウ生成時に
   一度だけ効く。
2. **動いていたのは CSS 側**。上部バーが `min-height: 66px` だったため、中身が高くなると
   **バーだけが伸びる**。実測: 文書名ブロックを 60px にするとバーは **66 → 77px**。
   ネイティブの玉はウィンドウ上端からの絶対位置（y=27）なので、伸びた分だけ中身が下へずれ、
   **「信号機が相対的に動いた」ように見える**。加えて `.primary-document-actions` が
   `flex-wrap: wrap` で、狭めたときに2行になると同じ現象が起きる余地があった。
3. **スクリーンショットからの断定はできない**。2枚は 1312×843 と 1307×953 で撮影範囲が違い、
   玉の位置差 (+10, +12) は「ウィンドウが画面上で動いたぶん」でも説明できる。
   画像だけでは切り分けられないので、**機構の方を潰した**（下記）。

**修正**

- 上部バーの高さを **固定**（`height: 66px` / `min-height: 0`）。伸びる余地を無くしたので、
  ネイティブの玉 y=27（= (66-12)/2、12px玉の縦中央）は**常にバーの縦中央**になる。
  実測: 2行の文書名（タイトル＋保存先）でも 66px のまま・中身の中心 32 ≒ バー中心 33。
  背の高い中身を強制しても 66px のまま。
- `.primary-document-actions` を `flex-wrap: nowrap` に（折り返しでバーを押し広げる余地を閉じる）。
- 契約テスト `workspaceChromeCss.test.ts`: CSS の `height: 66px`（`min-height` ではない）と
  Tauri の `y` を両方読み、**`y === (66 - 12) / 2`** を検査する。

補足: 2枚のスクショを撮り直すときは、**ウィンドウを動かさずにサイズだけ変える**か、
ウィンドウ単体のキャプチャ（⌘⇧4 → Space）にすると、撮影範囲のズレと実装のズレを分けられる。

## 追記2 — テーマ切替だけで信号機が動く（2026-09-11 第3報）

実機で「**テーマを切り替えただけ**で信号機の位置がズレる」との連絡。2枚（起動直後 / テーマ切替後）を
画素で測ると、**窓のサイズはほぼ同じ（1289×830 / 1287×828）なのに玉が (+12, +5) 動いていた**。

### 原因（コードから特定）

- ネイティブ側に実行時の位置変更は無い（`tauri.conf.json` の生成時に一度だけ効く）。
- 一方 **テーマ変更は窓の OS 外観（appearance）を変える**:
  `useAppPreferences` の effect が `setCurrentWindowTheme(...)`（= `WebviewWindow.setTheme`）を呼ぶ。
  macOS は外観が変わると**タイトルバーを組み直し**、そのときに
  `trafficLightPosition` の指定が失われて既定位置へ戻る。
- つまり「起動直後」も同じで、**マウント時の effect が不要な外観変更をかけていた**
  （config は `theme: "Dark"`。アプリのテーマが暗系なら設定と一致しているのに毎回呼んでいた）。
- Tauri 2.11 の**公開APIはウィンドウ生成時にしか位置を設定できない**（`set_traffic_light_position`
  は tauri の公開面に無く、`tauri-runtime-wry` の内部命令としてのみ存在する）。

### 対応（不要な外観変更を止める）

新モジュール `src/features/app/windowAppearance.ts`:

- **生成時の設定と同じ外観なら呼ばない**（`WINDOW_CONFIG_THEME = "dark"` = config の `theme`。
  定数と config の一致はテストで固定）→ 既定（暗系）の起動では**窓を触らない**。
- **同じ基調のテーマ間でも呼ばない**（例: 森の夜 → CRT。見た目は CSS が担う）。
- 結果、窓の外観を変えるのは「**明 ↔ 暗をまたぐ切替の1回だけ**」になる。

### 残る制限（正直に）

明 ↔ 暗をまたぐ切替では、窓の外観を合わせるために macOS がタイトルバーを組み直すため、
**信号機が既定位置へ戻り得る**。位置を再適用する公開APIが無いため、この1回は消せない。
選択肢は (a) この1回の移動を受け入れる / (b) 窓の外観を暗に固定して安定させる
（代わりにライトテーマでもネイティブの保存パネルが暗くなる）/ (c) Tauri が実行時の
位置設定APIを公開するのを待つ。
