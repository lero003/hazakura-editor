## 決定（2026-09-11・オーナー）

実機で「左上の信号機の位置と、隣の文書名との距離が気持ち悪い」との指摘を受け、
`traffic-light-tuning.html`（同じ寸法で描き直した調整ウィジェット）で確認して決めた。

**その後（同日・第3報で撤回）**: `trafficLightPosition` の指定は**削除した**（＝macOS標準の位置）。
指定していると、テーマ切替で窓の外観が変わったときに macOS がタイトルバーを組み直し、
指定が失われて標準位置へ戻る＝**切替のたびにボタンが動いて見えた**。標準位置なら、
外観が変わって組み直されても**同じ場所へ戻るので動かない**。オーナー判断も「変化しないこと優先」。

| 項目 | 決定値 | 旧 | 反映先 | 再ビルド |
|---|---|---|---|---|
| 信号機の位置 | **指定しない**（macOS標準） | x=20 / y=27 の指定 | `src-tauri/tauri.conf.json` | **必要**（ネイティブ） |
| 文書名の左位置 | **127px** | 84px | `--toolbar-document-inset`（workspace-chrome.css） | 必要（同梱のCSS） |
| 上部バーの高さ | **66px 固定**（`min-height` をやめた） | min-height: 66px | 同じCSS | 必要 |

文書名の 127px は、macOS標準の信号機（左から約20px・12px玉×3＋8px間隔＝右端 約72px）より
十分右なので、そのまま有効。契約テストは「指定が無いこと」と「127px が右端より右」を検査する。

根拠（実測）: モックの玉は窓の左から20px・11px玉・18pxピッチで、文書名は左から127px
（その手前93pxに切替アイコン）。旧アプリは右端73px・文書名84px＝**距離11px**しかなく、
モックの「次の要素まで24px」に対して詰まっていた。変更後は右端72px・文書名127px。

確認（実機fixture・ダーク）:

| 幅 | padding-left | 文書名の左 | モードナビ | 右の操作群 | 重なり・はみ出し |
|---|---|---|---|---|---|
| 1440×850 | 127px | 127 | 639（中央） | 924 | なし |
| 1024×748 | 127px | 127 | 446 | 701 | なし |
| 960×640 | 127px | 127 | 414 | 669 | なし |

契約テスト: `workspaceChromeCss.test.ts` が CSS の 127px と Tauri の x=20/y=27 を**両方読んで**
「信号機の右端 < 文書名の位置」を検査する（数字を2箇所に書かない）。

## 追記 — 「起動直後と操作後で信号機が動いて見える」（2026-09-11 第2報）

実機で「ボタンの位置が相対的に動いていく」「起動時とそれ以外で別の指定がありそう」との指摘。

**調べたこと**

1. **ネイティブ側は一度きり**。`src-tauri/src/lib.rs` の `on_window_event` は
   Apple Assist ウィンドウの閉じ処理だけで、**実行時に信号機を動かすコードは無い**
   （`set_traffic_light_position` の類も無し）。`trafficLightPosition` はウィンドウ生成時に
   一度だけ効く。
2. **動いていたのは CSS 側**。上部バーが `min-height: 66px` だったため、中身が高くなると
   **バーだけが伸びる**。実測: 文書名ブロックを 60px にするとバーは **66 → 77px**。
   ネイティブの玉はウィンドウ上端からの絶対位置（y=27）なので、伸びた分だけ中身が下へずれ、
   **「信号機が相対的に動いた」ように見える**。加えて `.primary-document-actions` が
   `flex-wrap: wrap` で、狭めたときに2行になると同じ現象が起きる余地があった。
3. **スクリーンショットからの断定はできない**。2枚は 1312×843 と 1307×953 で撮影範囲が違い、
   玉の位置差 (+10, +12) は「ウィンドウが画面上で動いたぶん」でも説明できる。
   画像だけでは切り分けられないので、**機構の方を潰した**（下記）。

**修正**

- 上部バーの高さを **固定**（`height: 66px` / `min-height: 0`）。伸びる余地を無くしたので、
  ネイティブの玉 y=27（= (66-12)/2、12px玉の縦中央）は**常にバーの縦中央**になる。
  実測: 2行の文書名（タイトル＋保存先）でも 66px のまま・中身の中心 32 ≒ バー中心 33。
  背の高い中身を強制しても 66px のまま。
- `.primary-document-actions` を `flex-wrap: nowrap` に（折り返しでバーを押し広げる余地を閉じる）。
- 契約テスト `workspaceChromeCss.test.ts`: CSS の `height: 66px`（`min-height` ではない）と
  Tauri の `y` を両方読み、**`y === (66 - 12) / 2`** を検査する。

補足: 2枚のスクショを撮り直すときは、**ウィンドウを動かさずにサイズだけ変える**か、
ウィンドウ単体のキャプチャ（⌘⇧4 → Space）にすると、撮影範囲のズレと実装のズレを分けられる。

## 追記2 — テーマ切替だけで信号機が動く（2026-09-11 第3報）

実機で「**テーマを切り替えただけ**で信号機の位置がズレる」との連絡。2枚（起動直後 / テーマ切替後）を
画素で測ると、**窓のサイズはほぼ同じ（1289×830 / 1287×828）なのに玉が (+12, +5) 動いていた**。

### 原因（コードから特定）

- ネイティブ側に実行時の位置変更は無い（`tauri.conf.json` の生成時に一度だけ効く）。
- 一方 **テーマ変更は窓の OS 外観（appearance）を変える**:
  `useAppPreferences` の effect が `setCurrentWindowTheme(...)`（= `WebviewWindow.setTheme`）を呼ぶ。
  macOS は外観が変わると**タイトルバーを組み直し**、そのときに
  `trafficLightPosition` の指定が失われて既定位置へ戻る。
- つまり「起動直後」も同じで、**マウント時の effect が不要な外観変更をかけていた**
  （config は `theme: "Dark"`。アプリのテーマが暗系なら設定と一致しているのに毎回呼んでいた）。
- Tauri 2.11 の**公開APIはウィンドウ生成時にしか位置を設定できない**（`set_traffic_light_position`
  は tauri の公開面に無く、`tauri-runtime-wry` の内部命令としてのみ存在する）。

### 対応（不要な外観変更を止める）

新モジュール `src/features/app/windowAppearance.ts`:

- **生成時の設定と同じ外観なら呼ばない**（`WINDOW_CONFIG_THEME = "dark"` = config の `theme`。
  定数と config の一致はテストで固定）→ 既定（暗系）の起動では**窓を触らない**。
- **同じ基調のテーマ間でも呼ばない**（例: 森の夜 → CRT。見た目は CSS が担う）。
- 結果、窓の外観を変えるのは「**明 ↔ 暗をまたぐ切替の1回だけ**」になる。

### 残る制限（正直に）

明 ↔ 暗をまたぐ切替では、窓の外観を合わせるために macOS がタイトルバーを組み直すため、
**信号機が既定位置へ戻り得る**。位置を再適用する公開APIが無いため、この1回は消せない。
選択肢は (a) この1回の移動を受け入れる / (b) 窓の外観を暗に固定して安定させる
（代わりにライトテーマでもネイティブの保存パネルが暗くなる）/ (c) Tauri が実行時の
位置設定APIを公開するのを待つ。
