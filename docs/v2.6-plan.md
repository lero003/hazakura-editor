## Product Intent

One line:

> 対象文章について AI と会話し、現在の未反映案を Diff で確認し、
> 納得した場合だけ本文へ反映する。

Three distinct responsibilities:

| Area | Responsibility |
|------|----------------|
| Conversation | 依頼、追加指示、短い応答、composer、プリセット |
| Diff review | 元文章と現在案、変更量、stale、破棄、`文書へ反映` |
| Editor | Markdown source / buffer。明示反映までは不変 |

This is Notion-like conversational revision, not a general chat, workspace
agent, or autonomous rewrite system.

## Active Spine

| ID | Slice | Done when |
|----|-------|-----------|
| **A-1** | **Proposal generation + Diff review** | Generate/stream into an unapplied proposal, show original-versus-proposal Diff, keep editor buffer unchanged, allow discard, retain presets |
| **A-2** | **Pinned target + multi-turn revision** | Pin tab/session/range/original on first request; follow-up instructions revise the current proposal and replace the same Diff review; allow new conversation |
| **A-3** | **Explicit apply from Diff** | Only the Diff review action may apply; stale target is rejected; the reviewed candidate is applied once with no post-apply Review Bar; no auto-save |
| **A-4** | **Two-region UX polish** | Conversation and Diff remain distinct at normal/narrow widths; keyboard, VoiceOver, locale, cancel, empty, failed, and stale states are verified |

Operating rule: **1 run = 1 ID or a smaller independently verifiable slice.**
A-1–A-4 source work is merged on `main`. The current run is the physical A-4
Assist gate; source, package, TestFlight, and publication claims remain
separate. The non-blocking A-3 hardening remains separate. Do not combine
physical validation with changes to the apply boundary.

## UX Pins

1. Long candidate text is not duplicated inside assistant chat turns.
2. The current proposal has one authoritative Diff review representation.
3. Additional instructions update the current proposal, not the editor buffer.
4. `文書へ反映` belongs to Diff review, not to an assistant message.
5. Closing, discarding, or starting over without apply leaves the document unchanged.
6. Narrow layouts may stack Conversation above Diff, but preserve labels,
   focus order, and separate scroll/decision responsibilities.
7. Operation feedback remains compact status, not chat transcript or provider log.

## Data And Boundary Pins

- `LocalAssistConversationSession` owns the pinned target, user turns, and
  `currentProposal` for the active in-memory session.
- `LocalAssistProposal` is unapplied review state. It is not an
  `AiEditTransaction`.
- The proposal keeps the bounded `actionId` selected when generation starts;
  editing the visible request text does not change the Apply provenance.
- `APPLY_AI_EDIT_TRANSACTION_EVENT` is accepted only when it carries the
  reviewed `proposalText` and explicit apply flag; it never starts a second
  model generation.
- Before apply, the main window revalidates tab session, document path, range,
  pinned original, and current target text. A stale request is rejected.
- The reviewed candidate is applied only once after that explicit action. A
  previous post-apply Review Bar state is cleared and no second Review Bar is
  queued for the same proposal; normal editor Undo remains available and no
  auto-save is performed.
- The initial implementation continues to build a bounded Revision Packet per
  request instead of persisting a model session.
- No conversation, proposal, prompt, or operation log is automatically saved.
- No network inference fallback, tool calling, workspace indexing, command
  execution, multi-file autonomous edit, or provider-add UI.

## Core AI (later backend, not this slice)

macOS 26 Foundation Models remains the initial backend. Core AI on macOS 27+
is a later capability path for stronger allowlisted on-device writing models.
The v2.6 conversation, proposal, Diff, and apply contracts should be model
independent so a later backend does not fork the UX.

Sequence:

```text
A-1 proposal/Diff separation
  → A-2 conversation
  → A-3 explicit apply contract stable
  → C-0 Core AI design spike
  → C-1 allowlisted model lifecycle
  → C-2 backend selection inside the same Local Assist UX
```

C-0 is a **pre-development lock** in `docs/core-ai-c0-design.md` (2026-08-27).
U-\* / H-1 / G-1 may proceed on `SystemLanguageModel`. Do not start C-1 until
identity + expanded manifest + Background Assets/AOT delivery. Do not start
C-2 until backend-specific availability and Rust-owned `selectedId`. Apply
stays frozen.

## Explicitly Out Of v2.6 A-1–A-4

- General-purpose AI questions unrelated to the pinned document target
- Workspace-wide chat/search, RAG, or persistent conversation database
- Docking Local Assist into the main editor (separate UX decision)
- Multiple simultaneous conversations or relaunch restore
- Whole-document context without explicit bounded user selection
- Core AI model download/catalog/selection implementation
- Arbitrary model URLs, unsigned model blobs, cloud inference fallback
- Tool calling, command execution, auto-apply, auto-save, background rewrite
- Multi-document autonomous editing
- Vertical writing, anydoc adoption, or residual Book depth as parallel scope

## A-3 Local Implementation Boundary

The reviewed local implementation implements only the explicit Diff-review apply
boundary:

- The Diff header owns `Apply proposal` and `Discard proposal`; conversation
  turns do not apply text.
- Apply sends the existing reviewed candidate, not a fresh prompt, through the
  existing apply helper. The main window updates the unsaved session buffer
  once, clears any older post-apply Review Bar state, and leaves saving as a
  separate user action.
- Generation partials are emitted only on the proposal status channel. The
  apply status channel is terminal-only for the explicit action.
- `HAZAKURA_ORIGINAL` is sanitized along with the other prompt boundary markers
  before a candidate reaches Diff or the editor buffer.

This is locally reviewed source work, not a release or device-validation claim.
A-3 follow-up hardening remains non-blocking and bounded: completion-time target
text revalidation, Diff failure/no-op Apply gating, and an Apply status watchdog.
A-4 physical streaming/cancel behavior, keyboard/VoiceOver/locale, and Core AI
remain separate gates. The finishing slice now includes accessible Diff column
headers, cancellation-specific feedback, and a probe-in-flight availability
message without changing the mutation boundary.

## A-4 Narrow-layout / Physical Validation Boundary

The merged A-4 source candidate is limited to the detached window's responsive
Diff layout:

- The shell has explicit rows for header, request form, presets, proposal Diff,
  feedback, and footer; the proposal owns the bounded remaining height.
- Diff rows and text cells can shrink to the window instead of imposing a
  `32rem` minimum, while the proposal body keeps its own scroll container.
- At `520px` and below, the two Diff columns remain equal-width and the change
  summary moves to a wrapped full-width row; line-number gutters become
  narrower.
- The Diff table exposes original/proposal column headers and associates each
  cell with its header; line numbers remain visual-only.
- Cancelled generation/apply events use a neutral `cancelled` feedback kind,
  and availability shows a checking message until the probe settles.
- No IPC, proposal state, apply, save, conversation, or target-validation
  behavior changes in this slice.

Focused frontend regressions are local evidence only. Detached-window
narrow-width interaction, keyboard/focus order, VoiceOver, locale,
streaming/cancel, and physical-device availability remain human-gated evidence
before a v2.6 release decision.
