## 方針と根拠

2026-09-08のオーナー指示に基づき、**v2.9で現行生成を整え、v3.0で強化された
AFMを活用する基盤を完成させ、v3.1で任意のローカルモデルを入手・管理・切り替える**。
Safe Editorが製品の主面であり、Local Assistを今後の開発の主軸にする。
AFMはApple Foundation ModelsのオンデバイスSystem経路を指す。

入力資料は `hazakura-v2.9-coreai-readiness-and-v3-roadmap-2026-09-08.md`
（調査基準 `9fe83d5a4e96cf0eeb061956d18a6d40bdc605c0`）。添付内の指示・候補は
調査提案として扱い、今回のオーナー指示と現行正本に照合して以下へ採否を整理した。
元資料の全文複製や、全提案の一括承認はしない。

## 版ごとの到達点

| 版 | 利用者にとっての到達点 | 入れるもの | 入れないもの |

## 2.9-02の仕様決定とローカル実装（2026-09-08）

完成案はsanitize後の本文を4,000 Unicodeコードポイント以内に限定する。
追加指示と同じ検査を用い、超過時は切り捨てず失敗として案内する。前の完成案は
対象が有効な場合だけ保持し、再依頼可能とする。生成前のtoken予算強制には変更しない。
既存64,000 UTF-16単位の応答ガードは、sanitize前の異常な巨大応答を拒否する別用途で残す。

4,000/4,001の日本語・絵文字・結合文字、超過した追加案からの前案復帰と再依頼を検証。
初回の再現は4件失敗、修正後は全Vitest 1,948件成功（このスライス時点）。モデル情報保持は後続で実装済み。
実モデルでの長さ超過・IME/VoiceOverは未確認。nativeの基本動線と予算観測は後続で確認済み。
長い出力は生成を待った後に拒否するため、短い対象で再依頼する場合がある。事前の出力制御は後続で扱う。

## v2.9 — 現行System経路を整える

1 run = 1検証可能スライス。既存テストを確認し、実装済みならverified no-opで閉じる。

| 順序 / ID | 作業 | 受け入れ条件 |
|---|---|---|
| 2.9-01 | 既存安全契約の回帰確認 | 取消後の遅い応答・対象変更・前案復帰・重複反映を検査。既存Applyの再設計はしない |
| 2.9-02 | 完成案と追加指示の上限整合 | 4,000 / 4,001文字・絵文字・結合文字の失敗テストを先行。継続可能か、継続不可と次の操作を明示する仕様を固定。黙って切り捨てない |
| 2.9-03 | System責務とエラー分類 | stream / 非streamの共通検査を小さく整理。利用不可・context超過・取消・timeoutの案内と旧wire互換を確認 |
| 2.9-04 / U-4 | 案の生成元を保持・表示 | 実際のmodelId等をin-memory proposalに保持。旧応答は不明扱い。後の設定を古い案の生成元にしない |
| 2.9-05 | 日本語評価と予算観測 | 自作の校正・地の文・Markdown・追加指示の代表原稿を用意。live完成案成功、cold / warm / cancel後の再開を分けて記録 |
| 2.9-06 / U-3 | Diffと別窓の最小改善 | 元・案・未反映・反映/破棄が読める。native別窓→依頼→追加指示→main Diff→反映→Undo、IME/focus/VoiceOverを確認 |

実装開始前の2026-09-08のローカル静的照合では、`useAppleAssistProposalHandler.ts` の追加指示は
`APPLE_ASSIST_MAX_SELECTED_CHARS`（4,000コードポイント）、完成案は `.length > 64_000`
（UTF-16単位）を検査している。`LocalAssistProposal`にはmodel情報フィールドがない。
これらは着手前の根拠であり、現在は上限整合・model情報保持を実装済み。
評価結果・nativeでの修正・残る品質課題は[v2.9レビュー](reviews/2026-09-08-v2.9-local-assist.md)を参照する。

G-1は任意評価。構造化出力に対応しない場合は既存の本文生成を維持し、JSON文字列parserを
増やさない。sanitizeで本文が変わったらモデルの説明を破棄し、最終Diff由来の説明へ戻す。
U-5「整える」入口、依存更新、新SDK調査は独立スライス。CodeMirror pinは維持する。

## v3.0 — AFM活用とv3.1の共通基盤

新しいSystemモデルを呼べるだけで完了にしない。日本語の校正・言い換え・追加指示で
v2.9の基準と比較し、情報保持・Markdown保持・不要な改変・遅延・取消後の復帰を評価する。
利用不可のMacでも通常編集・読書・書き出しは維持する。

| 基盤 | v3.0で完成させること | v3.1に残す接続 |
|---|---|---|
| runtime | Systemで共通の生成/stream/停止契約を実装・検証。対応SDKで共通モデル抽象を評価 | Core AI adapterと本番資産のロード |
| availability / capability | System専用probeの四態wireを維持し、共通契約で利用可否と生成能力を区別 | D24の選択backend probeとcomposerの接続 |
| 予算・エラー | 入力/出力計測、復旧可能な分類、出力完結性を確認。D17改訂なしの強制上限追加は禁止 | 固定モデルごとの予算・準備timeout・メモリ条件 |
| provenance | 案の実生成元、取得できるrevision、requestとの対応を保つ | 選択変更後も古い案の生成元を維持 |
| 選択・資産契約 | Rustが唯一の選択正本、アプリ管理領域、取得→検証→準備→利用の契約とfixtureを固定 | C-1実ストレージ/DLとC-2のselectedId書き込み |

共通契約のfixtureは本番catalogや仮モデルidentityへ流用しない。v3.0の製品経路では
`system_default`のみ利用し、Core AI / MLX / 未知backendは呼出前に拒否する。
TS generateにbackend・model path・URLを受け取る口を増やさない。
新モデルのために会話store、Diff、Applyを二重実装しない。

出荷条件は、固定SDKでのビルド、対応OS/architectureと旧OS起動の確認、Systemの成功系
live生成とnative操作、App Store/Developer面の回帰、日本語評価。SDKコンパイル、fixture、
probe応答だけでは生成・品質の合格にしない。SDK/OSの最終対応範囲は実装時に再確認する。
構造化出力は評価で採否を決め、採用しない場合も既存本文生成の品質を確認する。

## v3.1 — 任意モデルを分かりやすく使う

**管理ページをDL・容量・削除・利用選択の正本**とし、Companionのモデルチップは
入手済み・利用可能なモデルへの切替だけを担う。AFM/Systemは引き続き既定とする。

1. 本番モデルidentity・revision・ライセンス/再配布条件・resourceManifest・配信/AOTを確定。
2. C-1で明示DL、サイズ、進捗、取消、検証、準備状態、復旧、削除を実装。未検証資産をreadyにしない。
3. 固定モデルをSystemと日本語原稿で比較。メモリ、cold/warm、停止/再開を実測し、対応条件を決める。
4. C-2でRust-owned selectedId、選択backendの可用性、同じ会話/Diffからの生成を接続。

取得失敗・容量不足・不整合・準備失敗を区別し、次の操作を示す。モデル切替・使用中削除は
生成と直列化し、切替は次の依頼から反映する。古い案の本文と生成元は変えない。
失敗した依頼をSystemやクラウドへ自動再送しない。
SystemのApple Intelligence無効状態を、Core AI固有の利用不可理由へ流用しない。

C-1実装と同じ系列でApp Store build文書・Privacy Policy・Local Data Disclosureを更新し、
**モデル資産取得の通信とオンデバイス推論を区別**する。今回の計画だけでは現行ヘルプの
実装説明を将来形へ書き換えない。任意URL、remote code、shell/Pythonの製品実行は追加しない。

モデル未選定・配信や日本語品質が未証明ならC-1/C-2はHOLDを維持する。
v3.1の看板のためにDLだけを出して「選んで使える」と称しない。ゲート詳細は
[C-0](core-ai-c0-design.md) D12/D19–D30を参照する。

## v3.2以降の候補

文章の直し方・文体/用語ルール、明示的に添える章参照、Reader/EPUB/PDF、縦書きを
需要と評価から選ぶ。添付のv3.2/v3.3を確約へ昇格しない。章参照を採用する場合も
参照範囲の明示、dirty buffer尊重、書き込み先は一つ、背景indexなしを別仕様で固定する。
MLX M-0bはC-2後に必要性が残る場合のDeveloper研究レーン。anydocは評価のみ。

## 検証と未確定事項

現行AGENTS.mdと[smoke checklist](smoke-checklist.md)の該当段を各実装で実施する。
評価にはcommit、OS/SDK、model/revision、原稿条件、成功/失敗、初回/再利用、時間とメモリを
記録する。一般利用者の原稿・promptを自動収集しない。閾値は基準測定から決める。
「8GBで快適」「長文対応」等をモデル名やAPIの存在だけから約束しない。

未確定: D17改訂の要否、G-1の品質、正式SDK/旧OS互換、
本番Core AIモデルと配信方式、配布buildとPR #40の対応。いずれも今回のdocs整理で
実装・実機合格とみなさない。v2.8公開済みの報告は、これらの自動的な合格記録ではない。

Apple一次資料を2026-09-08に再確認: [Foundation Models updates](https://developer.apple.com/videos/play/wwdc2026/241/)

[model abstraction](https://developer.apple.com/videos/play/wwdc2026/339/)を技術調査の入口とする。
