# v3.1以降の執筆体験 — メモ・縦書きの計画詳細

Status: Planning / メモ・縦書きの方向性採用、詳細設計は未確定
Scope: v3.2後のメモ・縦書きと条件付きAI支援。版番号・出荷を確約しない
Authority: Advisory（採用方針は `roadmap.md`、製品境界は `product-brief.md` と `security-boundary.md`）
Last reviewed: 2026-09-26

## 提案の要旨

> 自分の文章を、自分のまま完成させられる編集室へ。

外向きの主コピー「Markdownで書き、本として読み、ローカルAIで整える。」は維持する。
次に深めるのは **書く → 読む → 直す → 届ける** 一連の仕事である。
直近はv3.2.0を依存関係の更新に充て、同一候補を実機で受け入れる。
2026-09-26のオーナー決定で、**見直しメモ・再開メモ・編集ルールメモと縦書き**を
v3.2後のロードマップへ採用した。メモはAIなしで使えるものから始める。
編集ルールは、ひな形に自分の言葉で注意や例外を書き足す形を中心にする。
必要に応じてAIにひな形や内容の候補を作らせる支援も条件付きで計画する。
AIによるメモ作成・編集方針を使った推敲・資料参照は、モデル能力とMLX経路の再評価後に扱う。
縦書きはLLM拡張と独立した柱とし、読書から出力へ段階的に進める。

この文書は既存の4本柱に上記の採用判断を反映した計画詳細である。
採用した方向性と、未確定のUI・保存方式・AI品質・追加候補を区別する。
現行キューと公開状態は `roadmap.md` / `current-status.md` を正本とする。

## 現在地と調整点

- Book Scope、Reader、位置への復帰、章単位 Diff、HTML / PDF / EPUB 書き出しは既存の基盤。
  ④で新たに検討するのは **縦書きでの読書と、その原稿を縦書きの刊行物へ届ける範囲**。
  EPUBそのものを初めて実装する計画ではない。
- **v3.1はApple審査を通過し公開済み**（2026-09-25オーナー報告）。
  公開を、個々のモデル・端末での品質が十分という証拠にはしない。
- 参考文脈を与えた既存の[モデル評価](reviews/2026-09-23-core-ai-context-probe/README.md)では、
  資料内の命令を生出力に取り込む例があり、長い文脈では生成も失敗した。②は①の延長として
  自動的に進めず、**参照中の命令に追従するリスクと日本語品質の評価**を独立した昇格条件にする。
- 校正時の数値・Markdown構造の保護は土台だが、機械的な保持検査だけで
  「口調が残った」「意味が正しい」とは判定できない。

競合にも部分的に重なる機能がある。iA Writerには Authorship と端末内 Style Check があり、
Ulyssesには校正と EPUB / PDF / DOCX 書き出しがある
（[iA Writerの機能](https://ia.net/writer/support/basics/features)・[Style Checkの説明](https://ia.net/writer)、
[Ulyssesの校正](https://help.ulysses.app/grammar-and-style-check)、
[Ulyssesの書き出し](https://help.ulysses.app/getting-started/first-steps-export-more)）。
「AI搭載」や「EPUB対応」を独自性と断定せず、**必要な資料だけを利用者が選び、
文体と原文を守りながら、読む・直す・確認する流れ**が選ばれる理由になるか検証する。

## 直近: v3.2.0 依存関係更新

v3.1はオーナー報告でApple審査を通過し公開済み。次の版の主題は
**依存関係をまとめて更新し、同じ候補を最後に実機で受け入れること**に決まった。
2026-09-25の開始時には、`vitest` / `@vitest/mocker` の
[GHSA-82fw-gwwq-j7x9](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9)
とRust `rustls` のadvisoryが監査に現れた。更新候補ではnpm・Rustとも既知の
脆弱性は0件になった。React・Tauri・CodeMirror・開発ツール・HTTP clientも
含むため、テスト合格から実機品質や出荷可否は推定しない。

`@codemirror/view` は6.43.13を**候補としてexact pin**し、旧6.43.2で回避していた
長い日本語の行消失・カーソルずれを実機で再確認する。SwiftPMのCore AI runtimeは
配布モデルとのrevision契約があるため維持し、MLX runtime追加は今回しない。
更新候補・例外・同一ビルドの実機マトリクスは
[v3.2依存受け入れドラフト](releases/3.2.0-dependency-acceptance-draft.md)にまとめる。

## MLXを再開する場合の技術境界

現行の[M-0a設計](mlx-m0-preflight-design.md)はSystem向けの内部backend wireまで。
MLXのモデル読込・推論はまだ追加されていない。**MLXはOS標準の推論経路を切り替えるだけでは
動かず、Swift側へMLXのライブラリとモデル用の処理を依存として組み込む必要がある。**
別の常駐サーバーが必須という意味ではなく、既存のSwift helper境界で扱う設計を検討できる。

[mlx-swift-lmの `MLXFoundationModels`](https://github.com/ml-explore/mlx-swift-lm/blob/main/Libraries/MLXFoundationModels/README.md)
には、既存の `LanguageModelSession` と接続する `MLXLanguageModel` adapterがある。
このadapterは **macOS 27 SDKと実行OS** を要する。直接 `MLXLLM` / `MLXLMCommon` を使う経路もあるが、
その場合は生成・streaming・取消と既存Diffへの接続をより多く自前で持つ。
どちらもSwiftPMのMLX依存、対応するモデル・tokenizer、版と権利の固定、
保存・メモリ・失敗時復旧・配布物の検証が必要になる。

手元のXcode 27 / macOS 27はadapter検討の環境条件を満たすが、
MLX packageの追加、compile、実モデル生成、出荷可否の証拠ではない。
再開時は **Developerレーンで1モデル・1動作の隔離評価** から始め、App Store対応を別に判断する。

## 1. 自分の文章に合う編集ルールをメモとして持てる — 方針採用

**利用者の仕事:** エッセイ・記事・製品説明を書くときの目的や語り口、表記の決め事を
ひな形に書き足し、迷ったときや日をまたいだ推敲で読み返せる。

### 1-a. 手で書き育てるひな形

最初は自由記述の **編集ルールメモ** を、AIなしで作成・編集・参照・削除できるようにする。
利用者が見出しや項目を増減でき、空欄や未決定の注意も残せるフォーマットを用意する。
自動検査に必要な固定schemaや、書き方を強制するルールエンジンにはしない。
以下はMarkdownで表したひな形の例であり、保存形式・ファイル名の確定仕様ではない。

```markdown
# この原稿の編集ルール

## 目的・読者

- 初めてこの話題に触れる人へ、体験を伝える。

## 語り口

- です・ます調。断定を強めすぎない。

## 表記・用語

- 「ユーザー」で統一する。

## 残したいこと・変えないこと

- 会話の素朴な言い回しを残す。

## 例外・迷っていること

- 引用文の表記はそのままにする。
```

原稿との紐付け、保存場所、持ち運びと削除の扱いは実装前に決める。
本文やfrontmatterへメモを黙って埋め込まず、書き出しにも混ぜない。
まず原稿単位で成立させ、複数原稿での共有やBook単位の扱いは利用を見て判断する。

**到達点:** 毎回同じ注意を思い出し直さずに済み、メモを見ながら自分で推敲できる。
メモを使わない通常編集も、そのまま続けられる。

### 1-b. AIにひな形や内容を提案してもらう — 品質再評価後の候補

利用者の明示依頼や、選んだ原稿・既存メモから編集ルールメモの候補を作る。
対象はメモ1件に固定し、新規案または更新Diffを確認して、利用者が編集・採用する。
AI案は本人が決めたルールとは区別し、承認前に既定の方針にしたり本文へ適用したりしない。
原稿の自動収集、好みの自動学習、メモの自動更新は含めない。
候補採用後もUndo・保存は明示的に扱い、本文の変更は別の依頼にする。

**到達点:** 方針を言葉にする手間が減り、誤って推定された口調や表記を本人が直せる。
生成失敗・取消・古い対象でも、既存メモや本文を失わないことを評価する。

### 1-c. 選んだメモを推敲へ使う — 作成支援とは別評価

どのメモを使ったかを依頼時とDiffで示し、実際に渡せる範囲を確認できるようにする。
初期評価は日本語の記事・製品説明の短い段落を優先する。長い章全体の推敲は、
モデルの文脈上限と実原稿での品質が確認できるまで約束しない。

最初は既存の明示的な推敲依頼だけに使い、校正専用の保持契約を曖昧に広げない。
用語表や「断定を強めない」はモデルへのお願いだけで保証せず、検出できる逸脱は
Diff付近に確認事項として示す。矛盾する方針、長すぎる方針、モデルの入力上限は
黙って省略せず、利用者に直せる形で伝える。過去原稿の自動収集、好みの自動学習、
追加学習は含めない。選択した過去原稿を参考にする案は②と同じ参照リスクを評価してから扱う。

**到達点:** 同じモデル・同じ原稿で方針なしの場合と比較し、望まない口調変更や用語変更、
やり直し回数が減る。数字・固有名詞・Markdown構造、Diff → 明示Apply → Undo、
AIを使わない通常編集の軽さを維持する。実原稿による人手評価を出荷判定に含める。

## 2. 選んだ資料や前後の章を踏まえて推敲できる — LLM再開後も条件付き

**利用者の仕事:** 記事の1段落を直すために、利用者が選んだ仕様説明や前章を読み取り専用で
参照し、食い違いや重複を確認できる。書き換え先は選んだ1か所だけ。

最初のスライスは **編集対象1か所 + 参考テキスト1件**。開いている未保存の参照文書なら
画面で見えている内容を使い、その旨を示す。そうでなければ許可済みファイルの読み取り時点を
示す。参照名、実際に渡せた範囲、上限超過・読取失敗を見せ、黙って切り詰めない。
指摘の根拠はアプリが読み取った原文の該当箇所へ戻れるようにし、モデルが作った引用を
事実の引用として扱わない。資料間の整合性チェックは事実の正しさの保証ではない。

参照資料は **命令を含み得る未信頼の文章**。モデルが資料中の命令を実行指示として扱う問題は、
表示上の「読み取り専用」だけでは解決しない。既存の文脈probeを再現する試験、
実原稿での品質比較、文脈量の上限、対象外の改変を拒む検査が通るまで、
資料参照付きの修正提案を製品の完成形として約束しない。必要なら最初は
根拠箇所を伴う **指摘だけ** に絞って評価する。フォルダ全体の自動読込、背景index、
複数ファイルへの適用は含めない。

**到達点:** 資料を貼り直さずに対象文の推敲へ進める。参照中の命令・長文・欠落・
未保存状態による失敗を評価し、検出できる異常では提案を止め、読めなかった範囲を
黙って省略しない。参照箇所と修正対象を利用者が確認できる。

## 3. 気づきを残して見直し、翌日も続けられる — 方針採用

### 3-a. 読書中の見直しメモ

**利用者の仕事:** Readerで通読中に「説明不足」「ここは残す」を短く記録し、翌日、
原文の位置へ戻って自分で修正し、終わった項目を閉じられる。

最初は単一文書の **手動の見直しメモ** に限定する。メモはReaderの静けさを壊さない
任意の操作で作成・編集・完了・削除し、未解決一覧から編集面へ戻れる。本文に独自記法を挿入せず、
書き出しにも混ぜない。翌日へ残すため保存は必要だが、保存場所、文書を移動したときの扱い、
端末間で持ち運べる範囲、削除方法は設計時に明示する。原文が変わり対応位置を確定できなければ
「位置を再指定」と表示し、似た文へ勝手に付け替えない。

AIの「指摘だけ」は手動メモの利用価値と導線を確認してから追加判断する。
提案を作るなら現行のLocal Assistの対象固定、Diff、明示適用と混同しない。

**到達点:** 通読を中断せず残した気づきへ再訪でき、位置が失われた場合も迷わず対処できる。
AIを使わない人にも単独で価値がある。

### 3-b. 次にやることを残す再開メモ

**利用者の仕事:** 「次は導入に具体例を足す」など、原稿ごとに次の作業を短く残す。
既存の読書・編集位置への復帰と合わせて、日が空いても書く意図を思い出せる。
まず原稿ごとに短いメモ1件を手動で作成・更新・削除できる範囲にし、
見直しメモと保存・移動・持ち運びの扱いを揃える。タスク管理や自動要約へは広げない。

**到達点:** 前回の原稿を一から読み返して作業を思い出す負担が減り、
短い執筆時間でも次の一手へ進める。メモの表示や記入は任意にする。

## 4. 日本語の原稿を縦書きで読み、届ける — 方針採用

**利用者の仕事:** Markdown原稿を保ち、読書面で仕上がりを確かめ、限られた形式で渡せる。

縦書きは2026-09-26のオーナー決定で採用した。まず **縦書きで読む** 表示を単一文書で作る。
元のMarkdownの位置へ戻れること、横書きとの切替、句読点・英数字・画像・表・リンクの
扱いを実機で確認する。次に既存EPUB出力の縦書き拡張へ進め、複数の閲覧環境で
崩れを確認する。ルビ・傍点・縦中横は原稿での表現方法と出力互換性を固定してから
段階的に扱う。縦書きの編集画面や自由なDTPは初期範囲に入れない。

仕事の文書向けの **DOCXへの書き出し** は別の検討候補として残す。
これは既存roadmapの Office → Markdown **取り込み評価**とも別の方向で、
利用者が渡す文書と受け手の要件を集めてから採用を判断する。
縦書きの採用をDOCX需要やLLM拡張の完了待ちにはしない。

**到達点:** 原稿を別の大きな制作ツールへ移す頻度が減り、対象形式で実際に
読める・受け渡せる。画面表示と書き出し結果の一致を断言せず、対応範囲を示す。

## 追加提案: 「仕上げ前の確認」を4本柱の接点にする

独立した大機能にせず、③④が使われた後に必要なら足す小さな導線。
書き出し前に **未解決の見直しメモ、既存の出力警告** を
一か所から見返す。確認済みでないからといって保存・書き出しを勝手に止めたり、
AIが「完成」を判定したりしない。各項目は原文やDiffに戻れることを優先する。
①のAIによる推敲を受け入れた後なら、用語・数字などの要確認差分も同じ導線に載せられる。
この導線が必要かは、実際に「最後の確認で何を見落としたか」を集めてから判断する。
読み上げを聴きながらメモを残す体験も追加候補とし、今回の採用範囲には含めない。

## 進め方と受け入れ条件

| 段階 | 主題 | 先へ進める条件 |
|---|---|---|
| **v3.2.0** | 依存関係をまとめて更新 | lockfile・回帰ゲート・同一候補の実機受け入れを完了 |
| v3.2後のメモ系 | 見直しメモ → 再開メモ → 編集ルールのひな形 | 保存・原文への復帰・移動時の扱いを設計し、通読と翌日の再開を最小スライスごとに確認 |
| v3.2後の縦書き | 単一原稿の縦書きReader → 縦書きEPUB | 横書き切替・原文復帰・日本語組版の実機確認後、出力を複数の閲覧環境で受け入れる |
| LLM研究を再開する場合 | MLX M-0bの隔離評価 | モデル・runtime・対応OS・ライセンス・実機品質・配布境界を固定 |
| 品質再評価後のAI候補 | メモの作成支援、メモを使った推敲、資料参照 | 1-bと1-cを別々に評価。原稿を参照する生成は②と同じ未信頼参照・文脈上限のゲートも通す |

メモ系と縦書きの版割り・相互の着手順は未定。両方を採用し、LLMの進展を待たずに設計できる。
AIなしの編集ルールメモを、AI支援の保留と一緒に止めない。MLX研究とLLM製品機能を一度に進めず、
汎用チャット、エージェント化、プラグイン基盤、モデル数の拡大は主題にしない。
通常編集の軽さ、IME、保存・復旧、Undo、
キーボードとVoiceOver、日本語の自然さは各段階の共通条件とする。

## 先に行う小さな検証

1. v3.2候補のnpm・Rust更新を個別に検証して同一候補へ統合する。
   CodeMirror・HTTPS画像・ネイティブ画面は専用の実機受け入れを記録する。
2. ①の手動メモと③について、通読から翌日の見直し、再開、ルールの追記を少数の実原稿で確認する。
   本文編集・ファイル移動・メモ削除時の扱いを決め、④は日本語組版と原文復帰から確認する。
3. LLM再開時は記事、エッセイ、製品説明など、実際に仕上げる原稿と
   「直してほしい / 残したい」判断例を集める。私的な原稿を同意なく収集・送信・診断へ混ぜない。
4. 1-bは本人の意図とAI案のずれ、確認・修正の手間、取消時の既存内容保持を評価する。
   1-cは同じモデル・同じ対象で方針なし/ありを比較する。採点対象は生成量でなく、
   口調の保持、不要な意味変更、用語・数値・Markdownの保持、採用までの手戻り。
   しきい値は基準測定の後に決める。SystemとCore AIの結果を一括りにしない。
5. ②は既存の文脈probe、命令を含む資料、長文、未保存参照、参照なしを別々に試す。
   原文引用の位置と提案の根拠を人が確認し、失敗時は対象本文を変えない。
6. ③④は実際の通読・翌日再訪・受け渡し現物で評価する。source試験やプレビューを
   実機、VoiceOver、IME、TestFlight、App Storeの受入へ読み替えない。
